# Askbase

**用自然语言查询数据库的分析 Agent。**

问一句中文，自动召回相关的表、生成 SQL、通过安全校验、执行查询，返回结果表格和建议的图表类型。

## 功能

**核心链路**

- 自然语言 → SQL，支持多表 JOIN、聚合、子查询、窗口函数
- 表结构自动采集：表/字段注释、枚举取值、外键关系、样例行
- 四级召回策略可切换：关键词（无需 API Key）/ 向量 / 混合 / **LLM 精排**
- 结构化输出：SQL、自然语言解释、建议图表类型
- **内置 Web 界面**：登录、提问、表格与图表渲染、SQL 详情、重试记录，无需前端构建
- **自纠错**：执行报错或结果为空时，把原始错误回喂模型重试；每一轮的 SQL 和失败原因都记录在响应里

**安全**

- SQL 必须通过四层校验：单条语句、必须是 SELECT（AST 判定而非字符串匹配）、危险函数黑名单、系统库拦截
- 执行走独立只读账号，数据库层面无法写入——即使应用层校验全部失效
- 5 秒查询超时、1000 行结果上限、超限标记 `truncated`

**工程**

- 统一响应体、全局异常处理、JWT 认证、OpenAPI 文档
- 端到端 Execution Accuracy 评估脚本
- Docker Compose 一键启动，GitHub Actions 持续集成
- 49 个单元测试

## 快速开始

### 前置要求

| 依赖 | 版本 |
|---|---|
| JDK | 21 |
| Maven | 3.9+ |
| Docker | 任意近期版本 |
| Docker Compose | v2+ |

### 启动

```bash
git clone https://github.com/<your-name>/askbase.git
cd askbase
# 只在 .env 不存在时复制——直接 cp 会把你已经填好的 API Key 冲掉
[ -f .env ] || cp .env.example .env

# 起 MySQL(3307) + Redis(6379)
# 首次启动会自动建 13 张表并灌入演示数据，约 40 秒
docker compose --profile mysql up -d

# 启动应用
mvn spring-boot:run
```

打开 **http://localhost:8080** ，用 `admin / admin123` 登录。

> 接口文档在 http://localhost:8080/swagger-ui.html 。

> MySQL 容器映射到 **3307** 而不是 3306，避免和本机已有的 MySQL 冲突。

### 配置模型（可选）

在 `.env` 里填入：

```bash
DEEPSEEK_API_KEY=sk-xxx      # 生成 SQL
DASHSCOPE_API_KEY=sk-xxx     # 表结构向量化
```

| 配置情况 | 行为 |
|---|---|
| 两个 Key 都填 | 混合召回 + 端到端问答，全部功能可用 |
| 只填 DEEPSEEK | 关键词召回 + 端到端问答 |
| 都不填 | 可浏览表结构与调试召回，问答接口提示未配置模型 |

**没配 Key 应用也能正常启动**——模型 Bean 按条件创建，缺配置只是少一个能力。

## 评估结果

内置 **50 条**评测用例（[`eval/golden_set.jsonl`](eval/golden_set.jsonl)），每条都带 gold SQL。

| 维度 | 分布 |
|---|---|
| 难度 | 简单 18 / 中等 22 / 困难 10 |
| 涉及表数 | 单表 21 / 两表 14 / 三表 11 / 四表 4 |
| 覆盖能力 | 聚合、分组、HAVING、JOIN、子查询、窗口函数、条件聚合 |

```bash
cd eval && python eval_askbase.py
```

**Execution Accuracy = 96–100%**（三轮：100% / 98% / 96%，即 48–50 / 50）。
波动来自模型偶尔多返回一列辅助列——数值正确，但严格比较列数时判为不一致。
单题耗时中位 **2.0 秒**（含一次精排调用），约 1800 输入 token + 200 输出 token。

### 准确率的演进

| 阶段 | 改动 | 题量 | EA |
|---|---|---|---|
| 初始 | gold 含诊断列 + 召回 topK=4 | 10 | 10% |
| 修评测集 | gold 只返回答案列 + topK=6 | 10 | 50% |
| 修评估脚本 | 浮点比较加容差 | 10 | 70% |
| 修 gold | Q5 的 avg_score 口径写错 | 10 | 80% |
| 扩充评测集 | 10 → 50 条 | 50 | 84% |
| 修题目歧义 | 5 处表述不严谨 | 50 | 92% |
| 补数据模型缺口 | 就业统计补专业级 + 工作城市字段说明 | 50 | 94–96% |
| **召回重排（rerank）** | 粗排取全部候选 → LLM 精排 | 50 | **96–100%** |

**教训一：优化之前先怀疑尺子。** 前三次"提升"（10%→80%）全部来自修评估本身，
没有一行代码改动模型行为。三个 bug 合计让准确率被低估 30 个百分点。

**教训二：扩充评测集之后，新题目的歧义立刻暴露。** 从 10 条扩到 50 条时，
有 5 道题因为表述不严谨被判错，模型其实答的是另一种合理口径（"最多"指条数还是人数、
"多少人"要不要去重、Top-N 遇到并列怎么办……）。**评测集的表述质量直接决定指标可信度。**

**教训三：数据模型的缺口比模型能力更容易被误判。** 最初以为"就业地点"字段缺失，
实际 `job_posting.city` 一直存在——只是列注释只写了"工作城市"，模型没能把它和"就业地点"联系起来。
改注释比加字段有效。

### 补的两处数据模型缺口

**1. 就业统计缺专业级数据。** `employment_stat` 声明了 `major_id` 字段（注释写着
"NULL 表示学院级汇总"），但生成器只产出了学院级行，专业级一行都没有。
任何"按专业统计就业率"的问题，JOIN 专业表必然返回 0 行。

修复时不只是补行，而是**把整张表改成从 `student` + `offer` 推导**：

```
已签约人数 = offer 里 sign_status='已签约' 的去重学生数（可验证）
升学人数   = 未签约学生里的一部分（业务表没有，只能在这里定义）
就业人数   = 已签约 + 升学
学院级     = 该学院所有专业级之和
```

改之前，这张表的就业率是拿随机系数编的，和 offer 表的实际签约情况对不上——
同一道题从 `employment_stat` 查和从 `student`+`offer` 推导会得到两个不同答案。
现在两种查法结果一致，验证脚本可以证明（学院级与专业级的不一致组合数 = 0）。

**2. 工作城市字段的语义没写清楚。** `job_posting.city` 的注释原本只有"工作城市"四个字，
而 `company.city` 是"总部所在城市"。问"留在陕西就业的比例"，模型看到两个 city 字段，
选了 `company.city`，然后自己判断"总部城市不等于就业地点"而拒答——**它是对的**。

修复是把列注释写清楚：

```sql
city VARCHAR(32) COMMENT '工作城市，即学生实际就业地点。判断"留在某地就业"用这个字段，
                          不要用 company.city（那是企业总部城市）'
```

改完之后模型能正确使用 `job_posting.city` 了。

### 召回重排：为什么它是最后一块拼图

补齐数据模型之后还剩下一个问题：有些问题需要的表<b>根本没被召回</b>。
问"签约工作地在西安的有多少人"，需要 `student` + `offer` + `job_posting`，
但 `job_posting` 在混合召回里排第 7，被 topK=6 切掉，模型于是拒答。

根因是**粗排的分数不可比**：关键词是覆盖率（0~10），向量是余弦（0~1），
加权融合后 10 张表的分数全挤在 2.4–3.0 之间。这个区间内的排序几乎是随机的，
调权重只会整体洗牌，而且没法解释为什么某张表该在前面。

重排换了个思路：**不再比较分数，而是直接问模型"回答这个问题需要哪几张表"**。
这是在做一个语义判断，不是数值比较，所以不受分数尺度影响。

```
粗排（关键词 + 向量，取全部 10 张候选，不截断）
        ↓
LLM 精排（问题 + 每张表的注释首句 + 字段名 → 返回排序后的表名数组）
        ↓
取 topK
```

**一个关键细节：候选说明必须带字段名。** 第一版只给了表注释首句，结果重排器
看到"招聘岗位表"这几个字，判断不出它和"工作地点"有关，还是漏掉了它。
加上字段名（`company_id, title, city, salary_min, ...`）之后立刻从第 7 升到第 3。

代价是每次问答多一次模型调用（约 +0.5 秒，300 输入 token）。相比主生成的 1500+ token，
这个开销可以接受。重排失败时会自动回退到粗排结果——**增强功能不能变成单点故障**。

| 策略 | EA | 单题耗时 |
|---|---|---|
| 关键词 | 最低 | 最快，无需 API Key |
| 混合（关键词 + 向量） | 94–96% | ~1.5s |
| **重排（混合 + LLM 精排）** | **96–100%** | ~2.0s |

### 剩余失败

| 题 | 症状 | 根因 |
|---|---|---|
| 课程平均分 + 平均起薪 | 偶尔多返回一列选课人数 | 模型偶尔附加诊断列，数值全对。三次调用里两次是 3 列、一次是 4 列 |
| 上市企业占比 | 偶尔多返回分子分母 | 同第一条 |
| 每学院薪资最高的专业 | 偶尔列数不一致 | 同第一条，窗口函数题的输出列数不稳定 |

> 原先"召回不到 `job_posting`"那条已通过**重排**解决（见上一节）。

> 试过加 prompt 规则"只 SELECT 问题所问的列"想修掉多余列，结果模型把本该展示的列
> 也删了（"每个城市薪资最高的岗位"只返回岗位名不返回城市），EA 从 88% 掉到 84%，已回滚。
> 也试过把 topK 提到 8（10 张表里召回 8 张），反而掉到 90–94%——表越多噪声越大。
> **这两个失败模式都说明：约束"少返回"比容忍"多返回"代价大；多召回比少召回更容易引入干扰。**

### 消融实验：两个功能最后都被关掉了

| 组 | 口径规则 | 自纠错 | 结果 |
|---|---|---|---|
| A | 关 | 关 | 基准 |
| D | 关 | 开 | 与 A 持平 |
| E | 1 条 | 关 | 低于 A |

- **自纠错零收益**：它修不了"SQL 执行成功但语义错"这类失败——没有信号可以回喂
- **口径规则负收益**：规则占用 prompt 注意力，模型开始幻觉字段名（实测出现 `o.job_posting_id`）

最终配置：口径层默认关闭（机制保留，可开对照），自纠错保留（对测试集之外的新问题有价值）。

### 关于可复现性

`temperature=0`，但**不是完全确定性**：同一问题多次调用，模型偶尔会多返回一列，
导致 50 条里有 1–2 条结果翻转（约 ±2 个百分点）。
所以 2 个百分点以内的差异不应被当成真实效应——**这也是为什么扩充评测集比微调 prompt 更值得做**。

## 关键设计决策

**为什么用 Spring Boot 3.5 而不是 4.x**

Spring 官方 2026 年 5 月统计：4.x 生产环境采用率不足 5%，3.x 刚过半，仍有超过 45% 的项目在 2.x。用 3.5 才是跟上企业现状。另外 Spring AI 2.0 强制要求 Boot 4，且 2026 年 8 月才 GA，把项目稳定性押在刚发布的库上不划算。

**为什么不用 Knife4j**

Knife4j 最新版 4.5.0 按 springdoc 2.3 编译，在 Boot 3.5 上会抛 `NoSuchMethodError`；把 springdoc 降回 2.3 又不支持 Boot 3.5。改用 springdoc 2.8.17 + Swagger UI，功能一致。

**为什么单独建一个只读数据源**

应用主库要写 `sys_user`、`query_log`，必须是读写账号；而执行模型生成的 SQL 必须用只有 SELECT 权限的账号。两者混用等于把删库权限交给了模型。这是纵深防御里最可靠的一层——即使应用层校验全部失效，`DELETE` 也会被数据库拒绝。

**为什么向量检索在内存里算余弦，而不是用 RediSearch KNN 索引**

只有 10 张表，全量比对是微秒级，上 KNN 索引属于过度设计。召回策略已抽象成 `SchemaRetriever` 接口，表数上万时新增一个 Redis KNN 实现即可，调用方不用改。

**为什么表注释写得这么啰嗦**

表注释和字段注释会被采集进 prompt，直接决定召回准确率和 SQL 正确性。用户问「薪资」，字段叫 `monthly_salary`，只有注释能桥接这个语义鸿沟。同一份 schema，注释写「岗位表」和写「招聘岗位表。薪资为月薪区间」，召回效果差一个数量级。

**为什么 SQL 文件里要写 `SET NAMES utf8mb4`**

MySQL 客户端的默认字符集取决于操作系统 locale。容器里没有 `LANG` 时会退化为 latin1，UTF-8 编码的 SQL 文件被当作 latin1 读入，中文会双重编码——数据看起来正常，但 `WHERE name = '计算机学院'` 永远匹配不上。在文件里显式声明，不依赖任何环境配置。

## 已知限制

- **评测集 50 条**，覆盖 10 张表的主要查询形态，但对边界条件和多轮追问覆盖不足
- **召回排序不稳**：10 张表都和"学生就业"相关，混合召回的分数挤在 2.4–3.0 之间，
  个别问题需要第 7 名的表却被 topK=6 切掉。需要更好的 embedding 或 rerank
- **模型偶尔多返回辅助列**：数值正确，但严格按列数比较时会被判为不一致（约 ±2pt 波动）
- **结果正确性无自检**：SQL 执行成功但语义错了（漏过滤条件、JOIN 位置不对）无法被发现，
  自纠错也修不了——这类错误没有可观测的信号
- **只支持 MySQL 单库**，不支持多数据源或跨库查询
- **没有多轮对话**，每次提问都是独立的
- **权限只有表级白名单**，没有列级或行级过滤
- **前端只做了单轮问答**，没有会话上下文；没有把查询历史持久化到数据库
- **演示数据是生成的**，业务相关性由生成器人工设定，不代表真实分布
